# プラン理解クイズ

現在の実装プランを短い対話に変換し、利用者が重要な判断を自分で組み立て直せるようにする。
用語の記憶や点数ではなく、別の場面でも使える理解を目標とする。

## 出題元となるプランの特定

1. 会話、計画管理ツール、タスク説明、実装の要約から、最新の関連プランを探す。
2. 古い提案より、実際に採用しているプランを優先する。
3. プランが明文化されていない場合は、確認できる文脈から簡潔に再構成する。
4. 採用するプランを確実に特定できない場合に限り、利用者へプランの提示を求める。
5. クイズの内容を変える前提があれば明示する。

冒頭でプラン全体を繰り返さない。
最初の問題に必要な文脈だけを示す。

## 出題項目の整理

利用者が実装を保守、デバッグ、拡張、レビューするために理解すべき判断を抽出する。

- 課題、制約、成功条件
- 採用する技術と、このプランでの役割
- コンポーネントの責務の境界と、データまたは制御の流れ
- 採用した実装方針と、見送った代替案
- 具体的な処理の仕組み
- リスク、境界条件、障害の起こり方、テスト

各判断を、影響の大きさと利用者にとっての新しさで並べる。
今後の選択に影響する事実を優先する。
雑学、構文の暗記、任意の名前、仕組みを理解しなくても調べられる詳細は除外する。

最初の一巡で扱う問題数を決めるが、全問題を先に提示しない。

- 小さな変更：2〜3問
- 中規模の機能：4〜6問
- 大規模または不慣れな設計：6〜8問

利用者が十分な理解を示したら、予定より早く終了する。
一巡を長引かせず、必要なら次の一巡を提案する。

問題の作成、回答の診断、難易度の調整では、[references/question-design.md](references/question-design.md)を読む。

## 一問ずつ進める

一回の応答では中心となる問題を一問だけ出し、利用者の回答を待つ。
問題と同じ応答で正解や解説を示さない。

次の形式を使う。

```text
問題 n：<焦点>
<現在のプランに結び付いた問い>

<必要な場合だけ、2〜4個の選択肢>
答えと、その理由を一言で教えてください。
```

利用者が因果関係を説明できる場合は、自由回答を優先する。
概念が新しい場合、代替案を混同しやすい場合、回答の負担を下げたい場合は選択式にする。
誤答の選択肢には、現実にあり得る結果や設計案を使う。

利用者が自由に回答する、ヒントを求める、先に説明を求める、難易度を変える、クイズを省略する選択を認める。
クイズの完了を、依頼された作業を続けるための暗黙の条件にしない。

## 回答の診断

選択した答えと、その理由の両方を評価する。

- **理解できている**：正しい選択に加え、因果関係またはトレードオフの根拠を説明できている
- **根拠が弱い**：推測、無関係な一般則、不十分な理由で正解している
- **一部理解**：仕組みの一部は理解しているが、条件や結果の一部を見落としている
- **誤った理解**：実装や保守で誤った判断につながる考え方に基づいている

利用者を評価する言い方は避け、次の順で応答する。

1. 判定を一言で示す。
2. 仕組みを平易な言葉で説明する。
3. 出題元のプランにある具体的な項目と結び付ける。
4. 実装、デバッグ、変更に及ぼす結果を示す。
5. 誤解を修正するための問題を一問だけ出すか、次の出題項目へ進む。

不正解だと告げるだけで終えない。
区別できていない点を特定する。
修正のための説明に、無関係な概念を詰め込まない。

## 難易度と進路の調整

- 正解後は、結果、責務の境界、代替案を問うことで難易度を上げる。
- 一部だけ理解している場合は範囲を狭め、因果関係を一段ずつ確かめる。
- 利用者が求めた場合は、答えを示す前にヒントを出す。
- 短く説明した後は、同じ問題を言い換えず、条件を変えた応用問題を出す。
- 誤った理解は、後で別の角度からもう一度確かめる。
- 利用者が根拠まで説明できる概念は省略する。
- 利用者の言語と技術水準に合わせる。
- 用語を知らないことだけを理由に、理解できていないと判定しない。

実装によってプランが変わった場合は、出題項目を更新する。
使われなくなった判断について出題を続けない。

## 一巡の終了

最後に、理解の状態を次の形式で短く整理する。

```text
理解できていること
- <判断と、利用者が示した根拠>

まだ曖昧なこと
- <特定の因果関係またはトレードオフ>

実装を見るときの観察ポイント
- <概念を具体化するファイル、責務の境界、動作、テスト>
```

利用者が求めない限り、数値で採点しない。
作業を続ける場合は、次の実装手順と、利用者が確認できる観察ポイントを結び付ける。

## 出題時の制約

- すべての問題を、現在のプランまたは実装結果に基づかせる。
- AIの推奨に同意できるかではなく、根拠と結果を説明できるかを確かめる。
- プランの制約に反しない代替案は、根拠があれば妥当な回答として扱う。
- 確認済みの事実、プラン上の前提、AIの提案を区別する。
- ライブラリの動作、プロジェクトの制約、コードの詳細を作り上げない。
- 変化しやすい技術情報を問題の前提にする場合は、適切な情報源で確認する。
- 各応答は、長い説明を読むより答えるほうが容易な長さに収める。
