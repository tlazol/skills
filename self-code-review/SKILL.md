# コード変更の自己レビュー

コードを変更した後、最終回答を返す前に次の手順を実行する。

## レビュー対象を確認する

- ユーザーの依頼と受け入れ条件を読み直す。
- 実際の差分と、変更箇所に関係する既存コードを確認する。
- リポジトリ内の規約、既存の設計、テスト方法を確認する。
- 自分の記憶や作業中の説明だけを根拠にレビューしない。

## 変更内容を評価する

次の順序で確認する。

1. **要件との一致**
   - ユーザーが依頼した動作を実現しているか。
   - 明示された制約と受け入れ条件を満たしているか。
   - 依頼されていない動作や公開インターフェースの変更が混入していないか。

2. **正しさ**
   - 正常系だけでなく、変更箇所に関係する境界値、失敗時の処理、状態の不整合を確認する。
   - セキュリティ、並行処理、互換性、データ損失のリスクは、変更内容に関係する場合に確認する。

3. **設計のバランス**
   - 現在の実装量を抑えることと、長期的な運用に耐えうる構造を両立しているか。
   - 現在の規模だけでなく、想定される運用期間、変更頻度、障害時の影響、既存の設計規約を考慮する。
   - 将来の可能性だけを根拠に、抽象化、設定項目、互換レイヤー、依存関係、ファイル分割を増やさない。
   - 一方で、コード量が少ないことだけを理由に、責務の分離、依存関係の整理、エラー処理、テスト可能性を軽視しない。
   - 分割や抽象化は、実際に存在する重複、結合、変更理由、運用上のリスクを減らす場合に採用する。
   - ユーザーの要件、既存コード、繰り返し発生している変更から予測できる範囲を超えて、将来を先回りしない。

4. **保守性**
   - コードの意図を名前と構造から読み取れるか。
   - エラー処理と責務の境界が明確か。
   - 一つの変更のために、関係のない箇所まで同時に修正する構造になっていないか。

5. **テストの妥当性**
   - 変更した振る舞いと、現実に起こり得る失敗を検証しているか。
   - 既存のテストで十分なら、重複するテストを追加しない。
   - 実装の内部構造だけを固定する、価値の低いテストを追加しない。

## 設計判断に迷う場合

単純な実装と長期的な運用に適した設計のどちらを優先するか、ユーザーの要件や既存コードから明確に判断できない場合は、独断で選ばない。

- 実現可能な案を二つか三つに整理する。
- 各案について、初期実装の複雑さ、保守コスト、変更への強さ、運用上のリスクを説明する。
- 推奨案と、その案を推奨する理由を示す。
- どの案で進めるかをユーザーに尋ね、回答を得てから実装または修正する。

既存の設計規約や明示された要件から選択が明らかな場合は、不要な確認を求めず、その判断根拠に従って進める。

## 問題を修正して検証する

- タスクの範囲内で修正できる問題は、報告だけで済ませず修正する。
- 関係のないリファクタリングや整形を混ぜない。
- 修正後は、変更に最も近いテスト、型検査、静的解析から実行する。
- 必要に応じて、より広い検証を実行する。
- 最後に差分をもう一度確認し、デバッグコード、意図しない整形、生成物、秘密情報が含まれていないことを確かめる。

## 結果を報告する

- 修正した問題と、実行した検証を簡潔に報告する。
- 実行していないテストや検査を、成功したものとして報告しない。
- 解消できない問題や検証失敗が残る場合は、その内容と影響を明記する。
- 問題が見つからなかった場合は、不要な変更やテストを作らない。
